一、总体评价：我觉得这份草案是“方向对、边界清、可分阶段落地”的

如果把目标定义为“不是重写压缩算法，而是把现有 VCF / gVCF 业务 payload 重新装进 AVS-G 容器语义里”，那你这份草案的路线是相当稳的。

一句话判断： 这不是“把现有 .gsc 机械翻译成 AVS 字段名”，而是在做一层真正的封装重构： 现有压缩 payload 尽量保留，外部组织方式切换到 AVS 的 HEADER / COMP_DATA / TAILER 语义，这个思路非常合理。

我最认可的 4 个点

  1. 把 外层容器 和 内部 codec 分开讨论，而不是混成一个问题。
  2. VCF 先按 chunk 对齐 AVS block，避免直接下钻到 row_block 粒度。
  3. gVCF 先保留 native V4 block codec，只替换外层封装，迁移风险最小。
  4. 把 header/sample/ploidy/n_samples 等全局信息从 .gsc main archive 上移到 HEADER，很符合 AVS 语义。

这份草案的核心价值

  • 把“现状是什么”与“未来怎么封”分开了。
  • 把“块数据”和“全局索引/参数”重新归位了。
  • 把现有 bool / size_t / 尾部匿名位图 这类实现细节，从未来协议层里剥离出来了。
  • 为后续 writer/reader 分阶段改造提供了清晰施工图。

二、先把三层关系讲清楚

这次讨论最重要的不是某个字段叫啥，而是要明确：标准 AVS-G 是封装框架，现有 .gsc / gVCF 是业务 payload，映射草案是二者之间的桥。

AVS-G 标准更关心什么

  • 有全局 Magic avsg
  • 有固定的 HEADER / COMP_DATA / TAILER 三段树
  • 索引与参数放在显式节点里表达

映射草案在做什么

  • 把现有 payload 重新放进 AVS 节点树
  • 把当前协议细节改写成显式全局参数/索引
  • 尽量不碰现有压缩主算法本体

三、为什么我认为这份映射草案是好的

它最大的优点不是“字段列得全”，而是决策边界划得清。

1. 明确新增 STD_TYPE=vcf / gvcf

这让 VCF / gVCF 进入 AVS 术语体系时不必伪装成 fq/fa/sam；同时你还把 BCF 放到 RAW_STD_SUBTYPE，这个判断也很合理，因为 BCF 更像载体差异，不是标准类型差异。

2. VCF 先按 chunk 粒度对齐 block

这个非常关键。当前 .gsc 已经有 chunk offset / min_pos / chrom 边界索引，直接拿 chunk 做 VCF_BLOCK_INDIV 是改动最小、收益最大的方案。

3. gVCF 先保 native block

不把现有 gVCF 的 RLE / Delta / Mask / Dict 整体拆碎，而是先 opaque 包装为 BLOCK_CORE_FIELDS / BLOCK_INDEX，这是最现实的路线。

4. HEADER 上移是对的

把 comp_v_header、comp_v_samples、ploidy、n_samples 从 main archive 前导区上移到 HEADER/VARIANT_BASIC，语义更干净，也更符合通用 reader 的理解。

5. GT 和索引归位了

你把 fixed fields / GT / other fields 放进 block payload，把 permutation、zero/copy、copy-origin map 放进 PARAM_GT，这正是“数据”和“全局解码辅助参数”的合理分层。

6. 显式 LOSS_MODE 优于 bool

当前 .gsc 的 mode_type 在语义上有使用门槛；改成 AVS 枚举字段后更直观，也减少读写两端误解。

总结： 你这份草案不是在把当前文件“套壳”，而是在做一次真正的协议层去实现细节化： 现有压缩结果尽量保留，当前 .gsc 中那些临时性、ABI 相关、位置耦合的组织方式，则被替换成 AVS 的显式节点与参数表达。

四、VCF 映射主线：这部分已经很成型

VCF 这条线是整份草案里最成熟的部分。它几乎已经把“现有 .gsc 的哪些东西属于 HEADER、哪些属于块数据、哪些属于 TAILER 参数区”说清楚了。

VCF：现有元素 → 建议 AVS 节点

我对 VCF 线的结论： 这部分已经不只是“想法”，而是很接近实施草图了。真正要补的不是大方向，而是 BLOCK_OTHERFIELDS 的组织方式和 GT 参数区的具体编码约束。

五、gVCF 映射主线：你的“先外包，不强拆”判断很稳

gVCF 这条线最大的风险，是为了追求 AVS 结构统一而把已经自洽的 native block codec 过早拆碎。你的草案没有这么做，我认为这是正确的。

你这条路线为什么对

  • 现有 gVCF 模块已经有独立 magic / version / block index 体系。
  • 它最大的价值是范围查询能力，不是节点名字漂不漂亮。
  • 短期最应该保的，是 native block + index 能力，而不是 AVS 形态上的完全对称。

你草案里的映射也合理

  • BLOCK_CORE_FIELDS：保留 native block codec
  • BLOCK_SAMPLE_FIELDS：对应现有 field hybrid 编码体系
  • BLOCK_INDEX：保留块级范围查询索引
  • PARAM_GVCF：承接内部版本号和块配置

gVCF：我建议继续坚持的原则

问题 建议 原因
是否把 gVCF 拆成和 VCF 完全平行的 fixed/core/sample 多个细节点？ 短期不要完全拆散。 现有 gVCF codec 已自洽，强拆会放大迁移成本。
gVCF 自身 magic/version 怎么处理？ 外层交给 AVS，内部版本号写到 PARAM_GVCF。 避免 AVS 外层和 native 内层双重 magic 并列。
块内索引是否保留？ 必须保留。 范围查询是 gVCF 线最关键的能力。
我的建议： gVCF 接入 AVS 的成功标准，不是“长得和 VCF 一样”，而是“外层封装一致、内部 native 能力不丢”。你现在的草案正好符合这个原则。

六、关键差距与尚未闭环的问题

大方向没问题，剩下的问题已经从“概念问题”收敛到了“工程设计问题”。这是好事，说明草案已经接近可实施状态。

1. BLOCK_OTHERFIELDS 要不要块内化

这是 lossless VCF 接入 AVS 的最大决策点。短期整体打包成一个 block payload 最省事，但中长期按块组织更符合 AVS 的 COMP_DATA 语义。

我的建议：
先允许两种实现路径并存，优先把接口语义定下来。

2. GT zero/copy 放哪

当前 .gsc 是 main archive + 匿名尾区混放；AVS 下显然更适合进入 PARAM_GT，但需要把编码模式写清楚。

我的建议：
在 PARAM_GT 中显式定义 ZERO_COPY_STORE_MODE 和 codec id map。

3. backend id 是否统一

HEADER_TEXT、SAMPLE_LIST、BLOCK_FIXED_FIELDS、BLOCK_GT、BLOCK_OTHERFIELDS 是否共享同一 backend registry，关系到 reader 复用程度。

我的建议：
统一。你草案里的这个判断是对的。

4. 当前 ABI 字段不能直接透传

bool、size_t、匿名文件尾位图这些，都是实现层细节，不能原样升级成对外协议字段。

5. current .gsc 的 offset 观念要被 AVS 接管

现在的 other_fields_offset / sdsl_offset 是扁平容器下的定位方式；AVS 外层既然已经有 BLOCK_INFO，就不应再把这两个值当协议字段暴露。

6. 需要把“块粒度”彻底固定下来

你已经建议首版按 chunk，这个建议非常重要。若这里不固定，后面 BLOCK_INFO、参数区和 reader 接口都会飘。

换句话说： 现在最大的风险不再是“这条路对不对”，而是“如果不先定块粒度、参数归属和 other-fields 的组织方式，后面每个人会按自己的理解实现，最终又会长出新的格式歧义”。

七、我建议的落地顺序

如果接下来真的要做实现，我建议不要从最难的地方开始，而是先把“外层能包起来”的部分做通。

Phase 1

先把 HEADER 迁上去

  • STD_TYPE / RAW_STD_SUBTYPE
  • LOSS_MODE
  • HEADER_TEXT / SAMPLE_LIST
  • PLOIDY / N_SAMPLES

Phase 2

按 chunk 封装 COMP_DATA

  • VCF_BLOCK_INDIV 对齐 chunk
  • BLOCK_FIXED_FIELDS
  • BLOCK_GT
  • lossless 时先允许 whole-blob BLOCK_OTHERFIELDS

Phase 3

把索引和参数迁入 TAILER

  • BLOCK_INFO：offset / pos / chr / count
  • PARAM_GT：perm / zero-copy / codec map
  • PARAM_OTHER_FIELDS：keys / fmt dict

Phase 4

再优化块内化与统一 backend

  • BLOCK_OTHERFIELDS 块内化
  • 统一 encoder registry
  • 补完整 reader / writer 协议测试

为什么这个顺序更稳

先包外层语义  →  再迁 payload  →  再迁索引/参数  →  最后做块内细化

原因：
1. 先把协议框架定住，避免一边改 writer 一边改接口定义。
2. 现有 codec 尽量后置改动，先保住功能。
3. 范围查询/样本查询等能力不会因为“为了套 AVS”而先被打碎。
