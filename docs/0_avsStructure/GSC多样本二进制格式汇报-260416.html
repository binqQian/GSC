四、Main Archive：文件主体的字段顺序

Main archive 从头部后开始，到 other_fields_offset 为止。它是解压时最核心的一段。

1. chunk 定位表

chunks_streams_size
chunks_streams[]
用来定位每个 fixed-fields chunk 的边界。

2. 基础参数

ploidy / max_block_rows
max_block_cols / vec_len
no_vec / copy_no / n_samples
决定 GT 维度和块划分。

3. 索引与 meta

chunks_min_pos[]
where_chrom[]
n_col_blocks / permutation / meta
支持范围查询、列分块和 header/sample 恢复。

4. fixed-fields chunk 串

各 chunk payload 直接顺序拼接
final 文件中无 per-chunk size 前缀
必须依赖 chunks_streams[].offset 定位。

主 archive 的关键字段组

字段组 代表字段 作用
chunk 边界索引 chunks_streams_size、chunks_stream_item 定位每个 chunk 在 final .gsc 中的绝对位置
GT 基础参数 ploidy、max_block_rows、max_block_cols、no_vec 解释 GT 行/列分块和向量数量
copy/zero 辅助信息 copy_no、used_bits_cp、bm_comp_copy_orgl_id 恢复 copy 行引用的 origin unique 行
范围查询索引 chunks_min_pos[]、where_chrom[] 辅助根据染色体和 POS 定位 chunk
列分块与排列 n_col_blocks、col_block_item、permutation entries 恢复 tiled 模式下每个列块的单倍体范围与排列
元数据 meta_magic、meta_backend、header/sample payload 重建 VCF header 和 sample 名列表

本轮整理中最关键的澄清点之一： final .gsc 的 chunk payload 前没有长度前缀；临时文件里有 uint64 size，但写入最终文件时只保留 payload 本体，边界完全依赖 chunks_streams[].offset。

一个很值得讲的实现细节

writer 在写完整个主体之后，会回到文件头重写真实的 other_fields_offset 和 sdsl_offset，并且再跳到 21 字节处回填 chunk 的绝对偏移。

fwrite(&mode_type, ...);

fwrite(&sdsl_offset, ...);

fseek(comp, 21, SEEK_SET);
for (auto cur_chunk : chunks_streams) {
    fwrite(&cur_chunk.second.cur_chunk_actual_pos, ...);
    fwrite(&cur_chunk.second.offset, ...);
}

五、Fixed-Fields Chunk：当前 writer 实际输出的是 GSCF V2

Main archive 内部并不是平铺的“字段流”，而是一个个 fixed-fields chunk。每个 chunk 目前都带有 row-block 目录，便于范围查询与按块解码。

关键常量

  • GSC_FIXED_FIELDS_RB_MAGIC = 0x46435347，按 little-endian 可视为 "GSCF"
  • GSC_FIXED_FIELDS_RB_VERSION_V1 = 1
  • GSC_FIXED_FIELDS_RB_VERSION_V2 = 2
  • 当前 writer 使用 GSC_FIXED_FIELDS_RB_VERSION_LATEST，即 V2
src/variant.h:356-361

reader 的兼容逻辑

  • 先看 chunk 起点 4 字节是不是 GSCF
  • 若是，则读取 version、目录项并建立 fixed_fields_rb_dir
  • 若不是，则回退到旧的 legacy 平铺格式
src/decompression_reader.cpp:2862-2987

为什么这部分重要

  1. 它解释了为什么当前解压器可以在新文件上做更精细的范围查询。
  2. 它解释了 fixed fields 和 GT 在 chunk 内部其实已经分段管理，而不是一坨连续未标注字节。
  3. 它是从“结构表”进入“可写解析器”的关键一环。
src/compressor.cpp:2983-3028 src/decompression_reader.cpp:3404-3459

六、GT Payload：不是文本 GT，而是变换后的索引流

这一部分通常最容易被误解。GT 在 .gsc 中不是直接保存 0/0、0/1 之类字符串，而是两条 bitplane 及其变换结果。

GT 两条 bitplane 的恢复语义

MSBLSB恢复字符
000
011
10.
112
src/decompressor.cpp:1005-1044

汇报时建议这样解释

  • no_vec 通常约等于 2 × 变体数
  • GT payload 本质上更接近“位平面编码 + 稀疏索引流”
  • 因此它与 other fields 的存储方式完全不同
  • 也因此需要额外的 zero/copy 位图辅助恢复

GT 的文件内落盘链路

Phase A 两条 bitplane
以 haplotype 为单位编码 0 / 1 / . / 2 四态。
→
Phase B 块内处理
经过排列、差分/XOR、稀疏化和 zero/copy 抽取。
→
Phase C 压缩为 GT row-block
每个 row-block 的 GT 索引流单独压缩。
→
Phase D 尾部追加 marker
最后追加 1 byte backend marker，reader 先取 marker 再解压。

GT codec marker

markerbackend代码位置
0BSCcase compression_backend_t::bsc
1Zstdcase compression_backend_t::zstd
2Brotlicase compression_backend_t::brotli
src/compressor.cpp:2897-2923 src/compressor.cpp:2825-2844

reader 侧对应理解

  • V2 chunk 中 GT 是按 row-block 分段存的
  • 解压时可直接用目录项的 gt_off / gt_size 取出对应 segment
  • 这让固定字段与 GT 的局部解码更自然
src/decompression_reader.cpp:3456-3459
汇报时可特别强调： GT payload 的最后 1 个字节不是数据正文，而是 codec marker；如果忽略这一点，手写 reader 很容易把解压输入流读错。

七、Lossless Part2：other fields 不是顺序字段，而是多流容器

当 mode_type = true 时，[other_fields_offset, sdsl_offset) 区间会保存 FILTER / INFO / FORMAT 等 other fields。这里不是 main archive 那种顺序布局，而是 File_Handle_2 管理的多流容器。

stream 是怎么注册出来的

  • 每个 key 会注册 key_i_size 和 key_i_data 两个 stream
  • 整体参数则注册为 part2_params
src/compression_reader.cpp:357-364
src/compressor.cpp:1343-1395

footer 是怎么读回来的

  • 先从尾部读固定 8-byte footer_size
  • 再跳到 footer 起点，恢复 n_streams 和每个 stream 的 parts
  • 最后按 stream 名反查对应逻辑流
src/file_handle.cpp:141-178
src/file_handle.cpp:178-255

part2_params 流中到底装了什么

  1. 先放 1 byte backend id，表示本参数块本身用什么 backend 压缩。
  2. 然后放压缩后的参数描述体。
  3. 解开后依次能读到：actual_variants[]、no_keys、key_gt_id、keys[]、backend、FORMAT dictionaries blob。
src/compressor.cpp:1343-1395 src/decompression_reader.cpp:551-625
组会上建议这样概括： lossless 模式下，GT 仍在 main archive 的 fixed-fields chunk 中；FILTER/INFO/FORMAT 等 other fields 则被拆到 part2 多流容器中。二者是并列的两条存储链，而不是都混在同一个顺序结构里。

八、SDSL Tail：zero/copy 位图在文件尾

SDSL 尾区是 GT 恢复链上不可忽略的一段。reader 会优先跳到 sdsl_offset，把四个 rrr_vector 先加载进来。

尾区顺序

  1. zeros parity 0
  2. zeros parity 1
  3. copies parity 0
  4. copies parity 1
src/compressor.cpp:340-379 src/decompression_reader.cpp:142-147

它的作用

  • 帮助判断某个 GT 行是否为全零行
  • 帮助判断某个 GT 行是否为 copy 行
  • 与 bm_comp_copy_orgl_id 一起恢复 copy 行的 origin unique 行

九、适合向导师汇报的风险点与下一步建议

除了结构本身，这些“格式工程风险”也值得在汇报里带出来，因为它们决定了文档今后能否演进为更稳定的对外规范。

风险 1：顶层无 magic/version

当前 reader 依赖固定读法和上下文约定来解释文件，不是强约束的自描述格式。

src/decompression_reader.cpp:101-123

风险 2：含 ABI 敏感类型

顶层头使用 bool，archive 中多处使用 size_t，跨平台稳定性不足。

src/compressor.cpp:113-115
src/compressor.cpp:140-143

风险 3：chunk 边界外显但不自包含

final .gsc 中 chunk 没有独立长度头；一旦边界索引损坏，局部恢复会更困难。

src/compressor.cpp:203-229

建议 1：做样例 hexdump

用一个极小 toy 文件，把 header、archive、part2、tail 的真实偏移打印出来，与 Excel 和本报告逐项比对。

建议 2：补 legacy 实测

当前 reader 兼容 legacy chunk，但汇报时可说明：新旧两条路径已读过代码，下一步建议用老样例再跑一轮验证。

建议 3：若对外协议化，先版本化

优先引入顶层 magic/version、去掉 size_t/bool，再考虑与 AVS 容器做更正式的映射。

向导师汇报时的推荐收束语： 目前这份整理已经把多样本 .gsc 从“仅能靠源码理解”推进到“可以按区段、字段、偏移、子格式分层讲清楚”的程度；下一步如果需要继续工程化，重点不是再补散乱说明，而是做样例核验和协议稳定化。
